A

主播视角 — Data Center 页面指标（1~11 项）

主播 + 公会长都能看到的基础指标

1. Current Diamond target（本期钻石流水）主播+公会长master 不变

一句话：主播在本结算周期里经手过多少钻石。

账户表
gain_diamond + send_gain_diamond + 结算记录表
SUM(diamonds) 已打款 + 兑换记录表
SUM(spent_diamonds) = 页面显示值

当前余额 + 已被结算扣走的 + 兑换花掉的 = 本周期真实钻石流水。在数据库里找不到这个值——它是三张表数据加起来的。

验证 SQL
-- ① 当前钻石余额
SELECT gain_diamond + send_gain_diamond AS 当前余额
FROM app_user_account WHERE user_id = ?uid;

-- ② 本周期已结算钻石
SELECT IFNULL(SUM(diamonds), 0) AS 已结算钻石
FROM app_payer_host_salary_detail_v2
WHERE user_id = ?uid AND status = 2
  AND settlement_time BETWEEN ?start AND ?end;

-- ③ 本周期兑换金币花掉的钻石
SELECT IFNULL(SUM(spent_diamonds), 0) AS 兑换花掉的钻石
FROM app_payer_diamond_purchase_detail
WHERE user_id = ?uid AND create_time BETWEEN ?start AND ?end;

-- 页面值 = ① + ② + ③

2. Diamond Balance（当前钻石余额）主播+公会长master 不变

一句话：主播账户里现在有多少钻石 = gain_diamond（收礼赚的）+ send_gain_diamond（后台赠送的）

SQL
SELECT gain_diamond + send_gain_diamond AS 钻石余额
FROM app_user_account WHERE user_id = ?uid;

3. Current Host Salary（主播档位工资）主播+公会长master 不变

一句话：档位工资 + 超出部分额外工资。不含 TG 奖励（TG 在第 4 项单独显示）。

算法 = 配置表 host_salary + 超出部分 (钻石 - 档位阈值) ÷ excessDiamondsRate
当前周期 → 实时余额匹配档位，现场计算
历史周期 → SUM((host_salary + excess_diamonds_salary) × salary_ratio)
页面值 = (host_salary + excess) × ratio，代码在 SalaryAggregationCalculator 做了合并和乘比例
⚠️
detail_v2 表存的是原始值（乘比例前），页面显示的是聚合后的值，两者不能直接对比！
验证 SQL
-- 当前周期：查钻石余额 → 匹配薪资配置表
SELECT gain_diamond + send_gain_diamond AS 钻石余额
FROM app_user_account WHERE user_id = ?uid;

SELECT level, diamonds, host_salary, host_tg_reward
FROM app_payer_host_salary_config_v2
WHERE diamonds <= {上面查到的钻石余额} ORDER BY diamonds DESC LIMIT 1;

-- 历史周期
SELECT SUM((host_salary + IFNULL(excess_diamonds_salary, 0)) * salary_ratio) AS 页面主播工资
FROM app_payer_host_salary_detail_v2
WHERE user_id = ?uid AND status = 2 AND settlement_time BETWEEN ?start AND ?end;

4. Current TG Reward（TG 奖励）主播+公会长master 不变

一句话：TG 渠道拉新的额外奖励。数据来源和第 3 项一样。

SQL — 历史周期（也要乘比例）
SELECT SUM(host_tg_reward * salary_ratio) AS 页面TG奖励
FROM app_payer_host_salary_detail_v2
WHERE user_id = ?uid AND status = 2 AND settlement_time BETWEEN ?start AND ?end;

5. Host Total salary（主播实际总工资）主播+公会长master 不变

一句话：主播最终能拿到的总金额。当前周期每次打开页面实时计算。

钻石余额 → 匹配档位 → (host_salary + excess + tg) × salary_ratio = 页面值

发放比例：有效天 ≥ 6 且 总时长 ≥ 12h → 100%，否则 → 70%（首周期保护不打折）

补充：salary_ratio（发放比例）影响第 3/4/5 项master 不变

① 首个周期保护 — app_agency_member.join_time 在当前周期 startTime 之后 → 1.00
② 达标 — 有效天 ≥ 6 且 总上麦 ≥ 12h → 1.00
③ 未达标 → 0.70（扣 30%）
验证 SQL
-- 有效天数和总时长
SELECT
  COUNT(CASE WHEN duration >= 7200 THEN 1 END) AS 有效天数,
  ROUND(SUM(duration) / 3600, 2) AS 总上麦小时
FROM app_live_user_site_daily_summary
WHERE user_id = ?uid AND dates BETWEEN ?start AND ?end;

-- 是否首周期
SELECT join_time FROM app_agency_member
WHERE user_id = ?uid AND status = 1;
-- join_time > ?start → 首周期保护，ratio = 1.00

6. Diamond salary level（薪资等级）主播+公会长master 不变

根据 Diamond Balance（第 2 项）去配置表匹配的等级。

7. Effective days（有效天数）主播+公会长master 不变

周期内每天直播满 2 小时算 1 天。来自 app_live_user_site_daily_summary 表的 duration >= 7200 记录数。

8. Host Advance Salary（已预支金额）主播+公会长master 不变

当前周期 → app_user_account.advance_salary_total_amount（美元）
历史周期 → SUM(advanced_amount) ÷ 100（注意：这个字段存「分」！）

9. Current Salary balance（工资余额）主播+公会长master 不变

= 第 5 项（总工资） − 第 8 项（已预支）

10. Agent shared salary（分给公会长的佣金）主播+公会长master 不变

当前周期 → 实时计算
历史周期 → SUM(agency_owner_salary) + SUM(agency_owner_tg_reward)

11. 钱包可提现金额主播+公会长master 不变

直接读 app_user_account.withdrawal_balance（美元）。跟选哪个周期没关系，永远是账户实时值。

= 全员 SUM(beansSalary + diamondsSalary + agencyCommission)。
代码路径：OwnerSalaryAggregationTemplate.calcTotalSalary — 每个人的佣金逐人累加，等效「全员主播薪资 + 公会长佣金」。

16. 公会已预支公会长master 不变

全员的第 8 项（已预支）加起来。

17. 公会工资余额公会长CHANGED

一句话：公会总工资扣掉已预支后还剩多少。

master：总工资 − 已预支 − 已借支（可能出现负数）
refact：总工资 − 已预支（不再减借支，最低 0）
🔍
代码路径：AgencySalaryDataCenterServiceImpl:45 — agentSalaryBalance = dto.totalSalary.subtract(advanceBorrow.advanceUsd)
VO 注释写的"总工资 - 借支 - 预支"是过时的，实际代码只减预支，不减借支。

18. 公会已借支公会长CHANGED

一句话：本期内、最后一次结算之后新借的净额。
净额 = type=1（借支）- type=3 且 settlement_id IS NULL（主动还款）。结算自动还款不参与。净额为负时服务层钳 0。

旧口径：app_user_agency.borrowed_amount（累计未还，结算后不清零）
新口径：最后一次结算之后的借支净额（结算后清零，未还部分转历史欠款）
📄 完整 SQL（代码 ContentAgencyOwnerSurplusDao.xml: sumPeriodBorrowAfterLastSettlement）
SQL — 三层 COALESCE 回退
-- 截止时间：V2 结算时间 → 盈余归档时间 → '1970-01-01'
SELECT COALESCE(SUM(CASE
    WHEN l.type = 1 THEN l.salary_amount
    WHEN l.type = 3 AND l.settlement_id IS NULL THEN -l.salary_amount
    ELSE 0 END), 0) AS 本期借支净额
FROM admin_content_agency_borrow_salary_log l
WHERE l.agency_id = ?aid
  AND l.to_user_id = ?owner_uid
  AND l.type IN (1, 3)
  AND l.create_time >= ?start
  AND l.create_time < DATE_ADD(?end, INTERVAL 1 DAY)
  AND l.create_time > COALESCE(
      (SELECT MAX(s.settlement_time)
       FROM app_payer_host_salary_detail_v2 s
       WHERE s.user_id = ?owner_uid AND s.agency_id = ?aid
         AND s.status = 2
         AND s.settlement_time >= ?start
         AND s.settlement_time < DATE_ADD(?end, INTERVAL 1 DAY)),
      (SELECT MAX(os.create_time)
       FROM app_payer_agency_owner_surplus os
       WHERE os.agency_id = ?aid AND os.status = 1),
      '1970-01-01');
-- 服务层 coerceAtLeast(0)

19. 公会可借支公会长CHANGED

一句话：直接读 app_user_agency.borrowable_amount（美元），不做任何动态扣减。字段是滚动余额：借支审批通过时已原子扣减、结算还款时加回。

06-09 版：字段 − 本期借支 − 历史欠款（双重扣减，借 100 少 200）
06-12 版：直接读字段，不再动态扣减
SQL + 恒等式验证
SELECT borrowable_amount AS 可借支美元,
       borrowed_amount AS 未还借支美元,
       borrowable_amount + borrowed_amount AS 总授信额度
FROM app_user_agency WHERE agency_id = ?aid;
-- 恒等式：borrowable + borrowed ≡ 总额度

20. 公会长总工资公会长master 不变

= 管理佣金（第 14 项）+ 自己作为主播的工资（beansSalary + diamondsSalary）。
代码：OwnerSalaryAggregationTemplate.buildPersonalCard:84 — totalSalary = owner.beansSalary + owner.diamondsSalary + commission

21. 公会长工资余额公会长CHANGED

与第 17 项共用 agentSalaryBalance 字段，代码路径完全相同。

master：总工资 − 预支 − 借支
refact：总工资 − 预支（dto.totalSalary.subtract(advanceBorrow.advanceUsd)）

22. 本期薪资公会长NEW

一句话：公会长本期未结算的实时收入 = 公会长总工资 − 本期预支。结算后自然清零。

当前周期代码（AgencySalaryDataCenterServiceImpl:57-58）：
realtimePeriodSalary = myPersonalCard.totalSalary - advanceBorrow.advanceUsd
→ 传入后做 coerceAtLeast(0)：预支 > 工资时按 0 展示，不会出现负数

历史周期：从 getSurplusDetailList 分页查归档表，匹配 cycleStart + cycleEnd 后读 periodSalary

23. 本期借支公会长NEW

与第 18 项完全同口径同值（PRD 要求两处统一）：本期内最后一次结算之后的借支净额，结算后清零。查询 SQL 见第 18 项。

24. 本期实际工资公会长NEW

= 本期薪资（#22）− 本期借支（#23）− 历史欠款（#25）。借多了或背着旧债时会显示负数。
代码：calculateOwnerSurplusForDisplay:149 — periodActualSalary = periodSalary - periodBorrow - historicalDebt

25. 历史欠款公会长NEW

一句话：公会长到目前为止还欠平台多少钱。

取该公会最新一条盈余归档记录（findLatest，不限周期）：
• 实际工资 < 0 → 历史欠款 = |实际工资|
• 实际工资 ≥ 0 → 历史欠款 = 0
⚠️
两套口径：
• 页面展示（calculateOwnerSurplusForDisplay）→ findLatest：最新归档，不限周期，含本期期中结算归档
• 结算归档（calculateOwnerSurplus）→ findLatestBefore：本周期之前的最新归档，避免同周期重复扣
📄 两套口径 SQL
SQL
-- 页面展示口径：findLatest（不限周期）
SELECT * FROM app_payer_agency_owner_surplus
WHERE agency_id = ?aid AND status = 1
ORDER BY cycle_end DESC, id DESC LIMIT 1;
-- 历史欠款 = period_actual_salary < 0 ? ABS(period_actual_salary) : 0

-- 结算归档口径：findLatestBefore（本周期之前）
SELECT * FROM app_payer_agency_owner_surplus
WHERE agency_id = ?aid AND cycle_start < ?cycleStart AND status = 1
ORDER BY cycle_end DESC, id DESC LIMIT 1;

常见疑问

排查三步走 · 分支判断 · 借支欠款流转

Q1: 页面值和数据库对不上？

三步走：① 当前周期工资是实时算的 — 查余额 + 配置表对照；历史周期查结算记录表 ② 检查单位（分 vs 美元）③ 确认时间范围和周期对得上。

Q2: Bug 是 master 还是 refact 引入的？

master 不变 有问题 → 线上也有。CHANGED / NEW 有问题 → refact 引入。

Q3: refact 到底改了什么？

工资余额不再减去借支（totalSalary - advanceUsd）。新增 4 个公会长专属指标。
06-12 修了三处：① 可借支直接读字段（修复双扣 Bug）；② 借支改为最后一次结算后的净额（type=1 - type=3 无 settlement_id），三层 COALESCE 回退；③ 历史欠款用 findLatest（不限周期）。
06-15 基于代码核对补充：第 22 项 coerceAtLeast(0) 保护。

Q4: Current Diamond target 为什么在单表里找不到？

它是 3 张表的数据加起来的（钻石余额 + 已结算钻石 + 兑换花掉的钻石），不直接存储。

Q5: 可提现金额为什么不随周期变化？

直接读账户余额，代表「以前结算打过来但还没提走的钱」，跟查询周期无关。

Q6: 主播和公会长看到的数字为什么不一样？

主播只查自己 → "公会"字段 = 自己的值。公会长查全员 → 真正的全公会合计。

Q7: App 端的工资会不会有延迟？

App 端每次打开页面都是实时计算的（读实时钻石余额 → 套公式），没有延迟。Admin 后台用快照表（每 10 分钟刷新），机制不同。

Q8: 借支了 100，可借支为什么只少 100 不少 200？

borrowable_amount 是滚动余额：借支审批通过那一刻 DAO 已原子扣了 100，页面直接读字段就是正确剩余额度。任何在字段基础上再减「本期借支/历史欠款」的算法都是双重扣减。

Q9: 结算后「本期借支」清零了，欠的钱去哪了？

两本账同时记：① 实际占额留在 borrowed_amount（额度不恢复）；② 展示转到第 25 项「历史欠款」（取最新归档的负实际工资）。两边金额一致，还清后同时归零。
